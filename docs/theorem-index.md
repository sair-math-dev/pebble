# 定理依赖 DAG 与 agent 探索

记录：TECH-0003；状态：proposed；更新：2026-09-09。

目标：把已检查定理编排成精确版本的依赖 DAG，由 agent 按研究目标自主选择入口、阅读节点、探索依赖和使用者，并在 Slate 中尝试所选定理。Pebble 提供图数据与探索 API；Clay 或其他客户端运行 agent；Slate 保留形式检查职责。

本次按用户建议调整主架构：DAG 是核心知识组织形式，名称/文本/符号索引负责寻找入口。向量召回和 reranker 保留为可评测的辅助方案，不是图探索的前置条件。

2026-09-09 后续确认：科研仓库完整基于 Git，成果及依赖必须能定位精确 commit；基础定理的新修改不能替换已检查依赖。下文据此区分 Git 历史、锁定包环境和定理证据图。本轮更新是设计修订，Git 托管及全局图 API 尚未实现。

## 1. 两项相连的任务

| 任务 | 输入 | 输出 |
| --- | --- | --- |
| 图构建 | 固定包、已检查声明及实际直接依赖 | 定理节点、精确有向边、证据出处、正反向邻接 |
| agent 探索 | 目标、允许环境、入口节点和探索预算 | 阅读过的子图、候选定理、需满足的条件及实际试用结果 |

目录和依赖来自 Slate 检查路径，不通过正则扫描 `theorem` 或让 LLM 猜正式依赖。PDF 中没有形式化绑定的陈述可以作为论文文本被搜索，但不能混入正式已检查定理 DAG。

DAG 是现有结果和证明关系的可重建投影，不是新的证明 IR；它不改变任何定理、证据或包身份。可以先做 API 供 agent 遍历，再提供局部图视图，无需首发渲染全站大图。

## 2. Slate 基线与当前集成状态

以下是设计初期对固定提交 `bab9a76e7864c33e4a90ec6f1b41ba972920d4bf` 的核查记录：

- `ResolvedTermNode` 包含 Bound、Const、App、DefApp，公式包含 Eq、Rel、And、Or、Imp、Forall、Exists 等；绑定上下文及定义身份是显式的。
- `TermId`/`FormulaId` 是带 arena 身份的内部句柄，不能原样存入跨进程索引。导出必须使用稳定的外部引用或自含结构投影，并绑定精确环境。
- `print_published_source` 已输出 FactId、canonical target、theory/target/certificate hash、依赖和假设闭包等，但当前打印是单结果视图，尚无完整包级定理索引接口。
- 所需新增工作是由 Slate 导出已检查声明的结构化目录，并把索引字段关联到相同检查结果；Pebble 不重新实现公式解析器或自行解码内部缓存来生成可信目录。

源码：[公式表示](https://github.com/sair-math-dev/loom-lang/blob/bab9a76e7864c33e4a90ec6f1b41ba972920d4bf/tools/slatec/src/fol/resolved_formula.rs)、[结果输出](https://github.com/sair-math-dev/loom-lang/blob/bab9a76e7864c33e4a90ec6f1b41ba972920d4bf/tools/slatec/src/main.rs)。该基线核查只做静态阅读。

后续本地 Slate 集成已实现 `slatec check-package` 的结构化包报告，包含声明、证据与检查器实际 `direct_dependencies`；真实快照发布闭环见 [验收记录](implementation-status.md)。这些导出仍不等于已实现全局精确端点映射、Git 来源绑定或可遍历定理图；下文对应表与图 API 均为设计。

## 3. 一条定理记录保存什么

沿用架构提案中的 `result_revisions` 模型，按声明种类区分 theorem、definition、axiom 等，避免建立另一套相互漂移的 theorem/result 真相；当前数据库尚无该表。索引单元是**一个精确版本中的可导出声明**；不将证明中每个局部 have 自动做成全球可导入定理。

| 字段组 | 内容与来源 |
| --- | --- |
| 身份 | result revision ID、package snapshot digest、ModuleId、module interface hash、FactId；与完整检查记录关联 |
| 命题 | 原始声明、可阅读的精确陈述、绑定变量/排序上下文、解析后的完整公式引用、target hash |
| 环境 | logic、ambient theory、definition environment 的精确身份 |
| 条件 | 显式参数和前提、逻辑/理论公理与经典原则等实际假设闭包；两者分别展示 |
| 符号 | 命题中用到的已解析函数/关系/定义身份，以及出现于前提或结论的位置角色 |
| 证据 | 检查记录、certificate/provenance 引用、直接证明依赖及完整闭包引用 |
| 学术信息 | 标题、作者、原论文、形式化贡献者、领域、来源说明和例子 |
| 自然语言说明 | 作者注释/论文中绑定段落；可选机器生成解释，记录来源、模型与审核状态 |
| 出处与使用 | 固定版本文件路径/源范围、引用落点、包安装与 import 信息 |

`FactId` 或 theorem name 单独不足以当全站唯一键。相同命题的两个证明、同名不同版本、不同理论里的同名符号均保留各自身份。可给相近版本做展示分组，但不得因此合并作者、假设或证据。

完整公式保留原作用域与连接词。只对可识别的外层参数和 implication spine 提取用于检索的前提/结论视图；不能把任意嵌套的析取、存在量词或蕴含都摊平成无作用域的条件列表。陈述中的前提与证明实际使用的基础公理是不同维度，例如“n > 0”和“依赖经典选择原则”不能混在同一个标签里。

## 4. DAG 的节点与边

选择边方向 `T → P`：T 的所选已检查证明直接使用了 P。向前读取 T 的证明基础，反向查询谁使用了 T。反向邻接是同一组边的查询视图，不额外制造反向依赖边。

核心节点是精确版本中的已检查定理及其证据绑定，跨包引用仍指向该精确节点。同名新版本保持独立；同一声明采用另一份不同依赖的证明时保留独立证据绑定，不能覆写历史出边。相同内容的例行重检只更新检查记录，不无谓复制图节点。

每条直接边关联所选证明/导出记录，并在已有 provenance 能支持时给出使用位置。必须从检查器实际依赖导出，不能把 source import 的整个模块、一个包的所有定理或传递闭包都当成直接使用边。现有输出若不足以解析到精确前提，需要补 Slate 导出接口；不以文件共现猜边。

| 关系 | 如何存储和展示 |
| --- | --- |
| `uses_fact` | 核心定理依赖边；必须具备精确端点和检查来源 |
| `uses_assumption` | 指向披露的公理/原则等叶节点，明确种类；不能显示为已证明 theorem |
| `mentions_symbol` / 定义引用 | 作为附属语义链接，帮助理解和定位入口，不混成证明依赖 |
| `cites_work` / `related_to` / 作者提出的推广关系 | 独立的关联层；可能有环，标明依据，不声明整个关联层是 DAG |

定理依赖 DAG、单个证明的内部 proof DAG、包依赖图是三个不同层次。局部证明节点不会自动成为可独立导入的定理；如需深入，agent 可以按需读取该定理的证明片段及 provenance。图记录的是当前所选证明用过什么，不是所有可能的推导关系，也不保证依赖集最小。

### Git 来源、版本与图规模

三种关系分别存储，不能把一种关系的边当作另一种：

| 图 | 节点 / 边 | 回答的问题 |
| --- | --- | --- |
| Git 历史 | commit → parent commit | 文件和项目如何演变；merge 保留多个历史父节点 |
| 包锁图 | 固定包版本 → 固定依赖版本，绑定各自 repo/commit/包路径 | 本次构建使用哪一套完整源码与环境 |
| 定理依赖 DAG | 精确声明及所选证据 → 实际直接使用的精确声明/证据 | 这个已检查证明依赖什么 |

来源绑定至少记录稳定 `repo_id`、精确 `commit_oid`、包路径、文件路径、ModuleId、声明定位及实际源码摘要。commit OID 同时记录所用 Git 对象格式；分支、tag、slug 和“最后修改提交”都不能代替来源绑定。结果还要绑定精确理论、定义、锁定依赖、工具链和所选证据；固定 commit 不会自动固定仓库之外的环境。这些字段是概念模型，尚未冻结为新增 schema。

同一仓库按选定 commit 的完整包快照检查。例如 c1 定义 A，c2 新增使用 A 的 B，则检查 repo@c2 中的 B 与该环境里的 A。A 的最后修改可能在 c1，但不能据此把它单独取自 c1 并随意混装其他版本。c3 改动 A 后，B 的源码即使没变，也必须在 c3 的新环境中重新获得相应检查状态；c2 的记录与出边保留。跨仓库依赖则在锁文件中明确选定目标 repo/commit/包及其完整锁定环境。

不会因为每个 Git commit 都存在，就自动复制该仓库全部定理图。先索引需要展示的已检查成果版本，保留每个版本独立的来源、署名、引用和状态；同一成果的声明、环境、所选证明及直接依赖绑定确实一致时，可共享不可变证据对象与邻接数据。只能按 Slate 实际提供的身份粒度核对；接口不足时保守保留不同修订，不能按同名、同命题或文件没改就合并。README-only commit 仍产生新的 Git 来源和研究元数据，完整树分类与正式发布要求也不能沿用旧整包报告跳过。

存储实际直接边，不展开所有推导路径或枚举未被选择的版本组合。对某个固定依赖视图，去重遍历的工作量按实际访问的节点和边计；版本绑定额外需要自己的索引。真实不同版本越多，存储与维护成本确实会上升；基础环境的变化也可能导致大范围重检，这些成本不能靠合并版本掩盖。界面可按成果名称分组历史版本，精确引用和依赖解析仍指向具体绑定。

### 基础定理修改与撤销

开发分支可以形成新 commit，正式发布版本及其 Git 绑定不可覆写。已有 B→A 的边不会因 A 的分支或 tag 更新而改指新版。更新依赖是显式锁文件变更，并重新执行完整的受控检查和发布要求。

发布应保留服务端受保护的 commit 引用与实际源码对象，普通 push 不得覆盖/删除这些引用；服务端治理的保护分支和发布标签禁止未经允许的强制更新。对象保留、备份恢复与垃圾回收共同保证已发布来源可取得，不能仅记录一个 OID 后允许它失去保留根。Git 存储或传输的内容损坏通过对象检查与独立源码摘要校验拒绝，不把新内容放到旧发布身份下。[Git 对象模型](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)、[Git 垃圾回收](https://git-scm.com/docs/git-gc)。这些 Git 保护机制尚待实现和验收。

改动命题、证明、理论、定义或假设都会改变需要检查的输入。把一项基础命题改为公理，或引入更强假设，即使新输入可被检查，也必须如实标明其种类与假设闭包，不能继承旧定理身份与旧证明说明。基础库的受保护发布审核要展示这类差异；签名或维护者身份不能代替数学检查。

若问题出在已发布的旧基础结果/检查器，保留历史内容并附加验证撤销。对依赖它的结果查询，必须按精确锁定闭包立即反映当前有效性，不能等异步索引或通知传播完成才停止显示有效通过。反向邻接用于找出需重检的使用者；受影响不等于其命题已经为假，应标为验证失效/待重检。自动化影响传播尚未实现，不能把现有版本撤销端点当作全局 DAG 撤销能力。

### 仓库删除后的图与引用

已发布节点和证明边不随开发 repo 删除而级联消失。节点继续绑定原 `repo_id + commit`、声明、环境及证据，从独立发布档案解析可获取内容；同名新仓库不替代任何旧端点。普通删仓且发布档案仍可访问时，已有证明与复用关系不变，不因此触发验证撤销。档案保留在发布时建立，无站内使用者的正式成果也保留；具体流程见 [仓库删除与发布归档](technical-research.md#仓库删除与发布归档)。

若发布内容被另行下架、清除或撤销读取权限，图查询立即服从当前状态，不从归档或摘要绕过限制。对有权知晓的使用者说明依赖当前不可获取。本地对已合法取得内容的检查与线上获取分开；新的正式发布仍须复查当前依赖分发授权和发布政策，缺少必需授权或输入则保持未就绪。不要将内容缺失表示为定理已被证伪或自动删除证明边。无法访问的节点及墓碑不向无权用户泄漏私有元数据。这部分尚未实现，既有本地目录删除后的快照复用验收不等于服务端删仓验收。

### 图构建与存储

拟用 `result_revisions` 与 `theorem_edges(source_node, target_node, proof_binding, origin_ref)`，按 source 和 target 分别建邻接索引。完整节点、实际声明与证据放在关联结果/对象记录中，边不复制整份命题。

发布一个子图时核查端点齐全、精确外部依赖已存在，并对新节点/边与已有依赖的组合进行环检查。未知目标、重复冲突或环意味着图未就绪，不可删掉不方便的边后声称完整。不要通过合并版本、同名定理或相同命题破坏无环性。底层正式检查与图发布状态独立：图提取失败不能伪造数学拒绝或完成状态。

只存直接边和必要的邻接索引；不预计算所有路径。遍历对已读节点去重，菱形依赖共享同一个节点。单次探索读取工作按实际访问节点/边和返回字节计，模型推理与检查成本另算。PostgreSQL 邻接表可作为第一种实现，是否需要专门图数据库由真实遍历负载决定。

## 5. agent 如何探索

### 入口与循环

agent 可以从已知定理、目标中的已解析符号、一个领域/包的目录或文本搜索取得多个入口；不要求从公理根开始全图遍历。目录和简单索引解决“从哪里进图”，图结构指导后续探索。

```text
目标 + 允许的理论/imports/锁定版本
  → 选择多个入口节点
  → 阅读结论、条件和邻接摘要
  → agent 选择下一步：展开依赖 / 查使用者 / 深读证明 / 换入口
  → 维护候选定理、待满足条件和已访问子图
  → 在 Slate 中实例化或尝试使用候选
  → 根据检查诊断继续探索，或返回候选与未解决项
```

沿依赖方向可以理解一个结论需要哪些基础，沿反向使用关系可以寻找基于这些基础的更强结论、应用或组合方法。邻居相关性由目标决定；共享某条基础公理不意味着两项研究相关。遇到高出度节点时分页读取、按领域/环境筛选或换入口，不把基础库全扫一遍。

agent 管理 frontier，并根据目标相关性、已知前提是否满足、环境兼容性和历史尝试决定展开谁。初始实现不固定成全图 BFS，也不要求训练专用导航模型。缓存节点读取；候选试用缓存绑定 node、goal、local hypotheses 与精确环境，避免换了目标/条件却复用不适用的失败结论。

预算包含节点数、边数、返回字节、工具调用、模型上下文和检查时间；预算结束返回已找到的候选、探索路径和未解决条件。未走到某节点或一次应用失败，均不意味着相关定理不存在或无用。

### Pebble 提供的最小工具协议

下列是工具职责提案，不是当前已经可调用的端点：

| 工具 | 返回内容 |
| --- | --- |
| `find_entries(query, symbols, environment)` | 有权读取的入口节点；支持名字、包/领域目录和符号查找 |
| `get_theorems(ids)` | 批量读取精确陈述、条件、环境、出处、导入信息和检查状态 |
| `neighbors(ids, direction, cursor, filters)` | 直接 dependencies 或 dependents，精确边依据、分页游标和节点摘要 |
| `get_proof_fragment(node, origin)` | 按需读取已有证明片段及 provenance，不一次发送整个证明库 |

Slate/Clay 另提供候选实例化与检查工具。Pebble 的图 API 不执行写作工作流，也不通过 agent 判断给定理颁发验证状态。

遍历游标绑定图快照/代际，旧节点内容保持稳定；每次请求仍复查当前权限和撤销状态，不能让固定图快照保留过期读取权限。邻接与计数不泄露私有端点，分页返回只声明授权视图中的完整性。公开可复用发布本身不能依赖读者无权取得的私有材料。

### 入口索引是配套能力

先支持精确名字、词项、已解析符号、所属包与理论。公式结构可以增加入口质量：变量名字可归一化，但保留排序、作用域、参数顺序和重复绑定关系；不能把 `f(x,x)` 当成 `f(x,y)`，不能让不同理论的同名运算合并。

需要自然语言入口时再评测语义向量：编码名称、精确陈述、条件和有来源的短解释，仍按定理粒度关联。LeanSearch 的 embedding/reranker 与 LeanDojo 的环境相关 premise selection 可以作为入口/候选选择的对照方法，不替代本方案的图探索主路径。[LeanSearch v2](https://arxiv.org/abs/2605.13137)、[LeanDojo](https://arxiv.org/abs/2306.15626)。

全局发现可返回需要新增依赖的候选；当前证明环境内探索则区分已有可见声明与需要安装/显式 import 的声明。传递证明依赖存在不等于 source namespace 已自动打开。私有 goal、局部假设和会话探索记录留在 Clay/客户端，除非用户明确选择提交；不会自动成为公共图节点。

## 6. 用现有 Slate 源码检验探索设计

库中存在下面两个定理，其结论相同，条件不同：

```text
LeftInverseUnique(a, b):  b * a = one -> b = inverse(a)
RightInverseUnique(a, b): a * b = one -> b = inverse(a)
```

来源：[代数例子](https://github.com/sair-math-dev/loom-lang/blob/bab9a76e7864c33e4a90ec6f1b41ba972920d4bf/examples/algebra/inverse_uniqueness.slate)。这里简写参数排序，仅说明检索设计，完整声明仍由原源码导出。

同一源码还有 `LeftInverseIsRightInverse(a,b): b*a=one -> a*b=one`，其书面证明引用 `LeftInverseUnique`。因此它提供了一个应由检查器确认并导出的具体候选边：

```text
LeftInverseIsRightInverse → LeftInverseUnique
```

这不是整份依赖图；其他依赖也必须从实际检查结果导出，当前并未运行图导出器确认完整出边。

agent 从 `LeftInverseUnique` 进入后，可通过反向邻接发现 `LeftInverseIsRightInverse`，读到它能从左逆条件推出右逆条件，再决定是否符合当前目标。若需理解左逆唯一为何成立，则沿依赖方向深入其证明基础。

对于目标 `b=inverse(a)`、已有条件 `b*a=one`，左逆唯一定理可作为优先尝试对象；右逆唯一定理可能需要先取得不同前提。图探索收集候选与路径，最终实例化和组合仍由 Slate 检查。

## 7. 发布与图的一致性

正式发布事务记录定理目录、直接依赖导出对象摘要和 outbox event。图构建按精确节点/证据绑定幂等写入，在端点和无环性检查通过后原子切换为可遍历的完整代际；不能把缺半边的构建状态当作完整图交给 agent。图延迟不修改发布的数学状态，精确结果页可直接读目录并显示图准备中。

公开搜索默认只选允许发现的正式版本；每个精确版本记录保留，按明确版本策略分组，锁定上下文查询不能被“最新版本”覆盖。撤回、验证撤销和访问权变化在读取时查当前状态，不能等待异步图/入口索引清理才阻止发现/下载。旧事件不得把已撤销结果重新设为公开可用。

更换 embedding/分词版本建立新索引代际，完成覆盖和质量检查后切换查询；不重发包、不生成新证明。尚未审核的自然语言说明与精确声明分字段，编辑说明不会暗中修改已验证目标。

## 8. 实施与评测

第一步完成 Slate 精确节点和直接依赖导出，验证全包覆盖、跨包端点、版本隔离及无环性。第二步实现批量节点读取、双向邻接、分页和简单入口查找。第三步让 Clay/外部 agent 在相同目标与预算下自主探索并试用候选；图 UI、语义入口增强另行迭代，不阻塞 API 验证。

对照同一数据和入口，比较平面候选列表与 agent 图探索；再评测多入口、双向遍历和候选试用反馈的贡献。固定模型、目标、允许依赖以及总 token/时间/工具预算，避免靠更大推理开销得出方法优劣结论。

样例包括：多定理组合、结论相近但前提不同、菱形共享依赖、高出度基础节点、不连通子图、版本冲突、同符号不同理论、私有端点和被撤销节点。评测可用候选覆盖、完成真实证明/导入的比例、访问节点与边、返回字节、延迟和无效探索比例；记录路径以解释失败。实际历史证明之外的合法替代方案也应算成功。
