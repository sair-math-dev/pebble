# Pebble 产品与架构设计

状态：首版提案。设计依据见 [需求映射](requirements.md)，实现细节见 [技术研究](technical-research.md) 与 [包管理及验证协议](package-verification.md)。本文描述目标产品及建议边界，不宣称这些功能已经实现。

当前优先级：Cargo 式包管理、构建检查、验证发布，加上 GitHub 风格的包页面、源码树、README、版本、依赖和结果浏览。社交与项目协作保留在产品方向中，完整 Git 托管和复杂审阅流程不作为包管理首发的前置条件。论文写作编辑器、实时共同编辑及相关同步基础设施不在本期范围。

## 1. 学术入口：研究问题与可复用结果

Pebble 面向研究者的核心承诺是：找到一个研究结果，理解它的条件，引用它，并直接把它用于自己的研究。项目组织研究，包交付成果，结果页承担学术发现与复用入口。GitHub 风格提供熟悉的导航，Cargo 式工具提供依赖与构建能力。

学术页面优先展示论文标题、作者、问题、主要结论和假设；owner/package、文件树及提交历史是辅助信息。不能只给软件包页面加论文分类标签，就认为完成了学术产品设计。

主循环是：发现已有结果 → 导入依赖 → 在外部环境研究并提交成果 → 项目审阅 → 验证 → 发布 → 被引用和复用。社交活动围绕这条循环组织。

一篇论文通常对应一个项目，但项目可以包含多篇文稿、多个可发布包或尚未形成论文的引理。默认简单项目只有一篇主文稿和一个包；复杂项目再展开多包结构，避免让初次使用者先学习软件工作区配置。

### 从 Hugging Face 借鉴的设计方法

Hugging Face 的 model card 在 README 上加入模型用途、局限、评估和结构化元数据，并让这些元数据参与筛选和关联；dataset card 描述数据内容和使用信息。值得借鉴的是围绕领域对象设计解释、发现和使用入口，而不只是复用仓库外观。这是我们的产品推论，不是对其增长原因的实证判断。[Model cards](https://huggingface.co/docs/hub/model-cards)、[Dataset cards](https://huggingface.co/docs/hub/datasets-cards)。

| 设计维度 | Pebble 的学术表达 |
| --- | --- |
| 用户寻找的对象 | 关于某个问题、满足某些条件的结论；也可以从论文或包进入 |
| 成果说明 | Research card：问题、主要结果、假设、与已有工作的关系、作者、引用和使用示例 |
| 领域专属预览 | 自然语言陈述、精确形式化命题、定义/假设、证明和依赖的按需展开 |
| 使用入口 | 阅读论文、引用精确结果、添加所属包、检查一个最小使用示例 |
| 成果之间的关系 | 科学引用、实际形式依赖，以及作者提出的推广/特例/替代关系，各自标明依据 |

### 第一版就需要的五项学术能力

1. **Research card 是默认详情页。** 作者填写研究问题、贡献说明、相关工作和署名；工具链导出声明、理论、证明状态与实际依赖。两类信息标注来源，作者不能填写一个自行生效的已验证状态。字段来自现有研究说明需求，不新增写作系统。
2. **单个结果可被发现、引用和复用。** 一篇论文中的引理有独立落点，关联论文位置、包版本与精确声明。引用可以细到该引理；安装仍以包为单位，不要求每个定理拆一个包。
3. **条件是阅读与筛选的核心。** 先看成立条件和结论，再看源码。例如研究者寻找某类概率界时，需要比较适用对象和假设，而不只是知道包名。首版支持文本、声明和已导出的理论/假设筛选；自然语言条件匹配只召回候选，实际可用性由精确导入和检查确认。
4. **学术归属独立于代码维护身份。** 原结果作者、形式化贡献者、包维护者分别展示；区分已有结果的形式化与作者声称的新研究成果。历史论文可以作为来源引用，不会因被引用就变成正式已验证发布。新颖性不由 kernel 或基本提交审核决定。
5. **学术引用与实际复用都可追踪。** “引用本文”来自明确引用记录；“这个结果被哪些已检查结果使用”来自检查器依赖。直接使用和传递依赖分开，不能把整个依赖树都计成直接引用。先提供反向列表，无需先实现全站交互式知识图。

例如用户从搜索进入某个不等式结果，读到准确假设，查看它在论文中的解释，再复制该结果的引用和所属包的添加命令，在本地最小示例中完成一次导入检查。这条路径同时交付学术理解、归属和复用；不是仅提供一个下载按钮。例子描述目标交互，不声称相关库已实现。

### 聚焦进入方式与差异化验证

首批面向需要寻找、复用和贡献形式化数学结果的研究者及其 agent；可以只阅读、引用或复用，不要求所有读者先学会发布形式化包。作者可以贡献经典结果的形式化、小型方法库或新结果，页面准确区分贡献类型。先让真实结果积累可用性，不把全学科知识图、完整 mathlib 迁移或自动判断新颖性作为启动条件。

冷启动内容必须人工检查研究卡和使用示例：先选两个不同主题的实际包，组织外部研究者完成找结果、辨认假设、引用、导入和检查任务。与同一内容仅提供普通 README/文件树的页面比较，记录任务完成率、条件理解错误、找到可用结果的时间与成功复用率。只有这些改善才支持学术差异化有效，新增标签数或下载量不足以证明。

后续社交围绕具体研究问题、结果澄清、复用反馈和贡献展开。当前无需增加论文编辑器、实时共同写作、通用应用托管或大而全的论坛来建立差异化。

## 2. 核心对象与身份

| 对象 | 职责与身份边界 |
| --- | --- |
| 用户 / 组织 | 持有项目和包命名空间；作者署名独立于账户操作权限 |
| 项目 | 长期研究与协作空间，有访问权限、Git 历史、文稿、讨论和发布记录 |
| 修订 | 一次固定的项目快照；分支名称可变，发布必须指向固定快照 |
| 文稿 | 外部提交的论文文件与阅读视图，关联精确结果；正式发布保存其快照 |
| 包 | 可安装的分发单元，具有稳定身份与人类可读名称；一个项目可维护多个包 |
| 包版本 | 不可覆写的源文件、数据清单、依赖锁定和导出接口快照 |
| 结果 | 引理、定理、定义或其他可定位贡献；关联准确包版本、声明与假设 |
| 发布 | 作者选择对外正式发布的研究快照，聚合文稿、包版本、贡献者、审核和验证记录 |
| 验证记录 | 某检查器在固定输入和政策下的检查结果；不能由作者自报成功生成 |
| 研究记录 | 对话、显式推理、工具事件与失败修复关系；有独立可见性和训练权限 |
| 挑战 / 贡献 | 社区研究任务及其提交，可以是证明、批评、反例或部分进展 |

显示名称、URL slug、版本号与内容摘要分别存储。转移或重命名项目保留稳定对象身份和旧地址跳转。精确引用绑定版本与结果身份，不能随分支或同名声明悄悄改变。

科学引用与机器依赖是两种关系：背景讨论可以引用一个未导入的研究；形式化证明的实际依赖则来自检查器。界面同时展示，不能把参考文献列表当作完整证明依赖。

## 3. 信息架构

全局入口优先是发现研究、搜索结果、浏览论文/包及个人收藏。发现页以领域、研究问题和近期成果组织；结果可回到所属论文和包。关注动态和通知随社交阶段加入，完整项目审阅不是首页首发前置条件。

项目页面建议包含：

- **研究概览**：Research card，优先展示学术标题、作者、研究问题、主要结果、最新正式发布、假设摘要及引用/使用入口。
- **论文**：已提交论文的阅读、下载、结果引用及版本对比。
- **结果**：可搜索的声明目录，查看精确命题、证明、依赖、假设和来源。
- **文件**：所选包版本的源码树、数据和工具配置；可链接外部 Git 来源。
- **讨论（后续）**：结果澄清、复用问题和研究讨论；完整项目改动请求与审阅后置。
- **发布**：版本记录、验证与提交审核状态、变更说明和安装方式。
- **设置**：成员、权限、包归属、训练选择与数据公开设置。

结果页面是产品的关键入口。上方给出人可读陈述和适用条件；下方展示形式化声明、验证范围、所属版本及精确引用；证明和依赖按需展开。平台不能把自然语言解释误标为检查器已经验证的命题。

## 4. 主要用户旅程

### 发现与复用

研究者搜索问题、概念或声明，先看到结果和条件，再进入所属论文或包。选择一个结果后，查看依赖及假设，与当前项目环境比较，随后添加依赖。初始版本先支持文本、元数据和声明索引；语义检索作为发现辅助，不提供逻辑兼容性承诺。

agent 使用同一搜索与检查接口，获得结构化声明、版本、来源和假设。安装成功不等于证明可用；Slate 必须检查精确接口及当前理论环境中的使用是否合法。

### 成果提交与项目审阅

作者在外部写作和研究环境中完成论文、代码和数据，通过 Git 或上传提交到 Pebble。平台保存固定修订，提供论文阅读、下载和精确结果引用。论文更新形成新的修订；已有发布引用保持绑定原版本。

改动请求集中展示提交文件差异、声明变化、依赖变化和验证结果。合并前可以要求指定合作者审阅；评论绑定修订及目标，源文件变化后标记过期。议题、PR 和研究讨论属于项目协作，不要求在线论文编辑器。

Clay 的写作与 AI 工作流不在本期 Pebble 实施计划中；目前只定义外部成果进入平台的接口，不选择共同编辑技术或文稿同步格式。

### 正式发布

作者选择固定修订和准备发布的包，填写研究说明，确认作者、授权、假设、数据来源和引用信息。系统执行验证与基本提交审核；两项均通过后，原子地建立发布记录并开放对应包版本安装。

开发中的公开仓库可以包含未验证草稿，但必须明确标为开发内容，不出现在正式已验证发布集合中。正式发布的全部形式化代码都要检查；仅检查主定理或作者选择的文件不足以通过。包边界、入口清单及检查覆盖策略需要在协议中明确，未知文件类型不能悄悄跳过。

研究方法、失败与部分进展可以作为讨论或研究记录公开并被引用；它们不会因此获得已验证包的身份。无形式化代码的材料也不能利用空检查结果获得“已形式验证”徽章。

### 学习与社交

支持关注研究者、项目和主题，收藏结果、订阅发布、讨论证明及提出复用问题。贡献者页面展示作者身份、维护贡献、审阅及可引用成果，保留真实贡献类型。

阅读结果时可展开前置定义、假设与依赖，进入 Clay 的学习会话。社区讨论、收藏数、引用数与验证状态分开显示；热度不改变验证结论，形式验证不决定科学重要性。

## 5. 发布、验证与撤回

发布候选有可审计的状态流：草稿 → 已提交 → 检查中 → 可发布 → 已发布。失败记录指向具体阶段和输入；修改输入生成新的候选，不能把旧检查结果搬到新内容上。

每次检查绑定源码与数据摘要、完整依赖锁定、Slate 工具链、检查政策、精确目标及检查器输出的假设闭包。构建任务和作者提交的清单都不拥有数学接受权；可信检查路径决定哪些结果已验证。平台服务负责确认记录确实来自受控检查流程并绑定正确输入，不能仅相信上传的布尔值或签名作者身份。

基本审核检查必填内容、格式、权利声明及使用说明，不评判新颖性或重要性。论文自然语言与形式化命题的忠实对应需要单独审阅，不能由“形式化代码通过”自动推出。开发假设、未解决结果及不符合发布政策的产物不得进入正式验证发布。

已发布版本不可覆写。更正产生新版本；撤回保留引用落点和原因。被撤回的版本不参与新的默认依赖解析，已有锁定版本显示状态并受明确政策约束。检查器漏洞或验证结论失效可追加撤销记录；内容身份不变，当前信任状态可变。必要的内容下架保留最小墓碑信息，不承诺违反删除义务的永久可下载。

## 6. 包管理与平台协议

建议本地客户端归 Slate，注册和分发服务归 Pebble。命令名与文件名尚不冻结。协议至少覆盖：

- 包与命名空间归属、版本列表、不可变内容定位和发布权限。
- 版本约束解析、依赖锁定、固定工具链和直接/传递依赖清单。
- 内容下载与摘要校验、认证、私有包权限和本地缓存。
- 发布候选提交、验证查询、正式发布、撤回及验证撤销查询。
- 结果定位、精确引用及可供 agent 消费的元数据。

版本号表达维护者的兼容性意图；实际接口和依赖身份仍需工具链检查。协议应允许离线重放已获得的内容和证据，但离线无法获知之后发生的撤销，客户端需显示状态检查时间。私有项目依赖不得经公共日志、搜索或错误消息泄漏；公开包不得依赖读者无权获得的私有材料而声称公开可复现。

Slate 的既有对象/缓存格式不是 Pebble 服务端数据库模型。跨仓库先定义有限的发布和验证适配接口，完成实际工具链能力核查后再冻结字段；不要求平台重新实现内核，不直接修改现有信任规则。

## 7. 私有研究与训练贡献

分别保存项目访问权限、研究记录公开选择和训练贡献选择。私有项目默认贡献训练遵循原始愿景，但创建、开启 AI 会话及修改设置时必须显著说明：私有访问不阻止训练使用，未发表研究可能因此失去保密性。用户可以退出训练贡献，并保留 BYOK；免费额度资格随贡献规则变化。

公开附加对话是额外的明确选择，不随正式发布自动发生。记录的是可见对话、显式人类推理和工具输入输出，不承诺取得模型隐藏推理。

每段可导出的材料需保留来源、参与者、授权范围、模型/提供商相关权限及验证状态。项目拥有者的开关不能代替第三方内容和协作者必要的授权；权利不明的材料不进入训练。后续协议必须明确设置变化的生效时间、待导出数据的撤回及已训练数据的处理边界，不承诺可以从已训练权重中自动消除影响。

训练导出是一条独立管线，失败记录带失败或未解决标签。受保护评估题目、变体及关联问题族在导出前排除；公开可见不等于可用于训练。

## 8. 仓库与服务边界

| 范围 | 建议归属 |
| --- | --- |
| 语言、编译器、可信内核、本地包管理客户端 | Slate repo |
| 项目托管、网页、项目协作、论文文件、注册分发、发布、搜索、权限 | 本 Pebble repo |
| 深度科研 IDE 与交互式 agent 会话 | Clay 产品边界；暂不另建 repo，先确定共用项目接口 |
| 模型训练、权重发布、推理 API、额度服务 | 独立系统，通过授权数据和身份接口连接 |

Pebble 内部建议先采用模块化单体应用与独立任务执行器。身份/权限、项目、论文阅读、项目协作、注册、发布、搜索和数据贡献是明确模块，但暂不各自拆成网络服务。验证任务运行不受信任的源码与构建工具，需要独立隔离执行、资源限制和最小凭据。

建议使用关系数据库保存事务性元数据，对象存储保存包源码快照、论文与数据；Git 仓库提供可选来源，后续自托管时保存完整修订历史，队列驱动验证和索引。搜索索引是可重建投影，不能作为发布状态或访问权限的唯一依据。发布跨存储采用先准备内容、再事务提交可见记录的方式；重试幂等，失败候选不得被安装。

具体组件建议与待验证假设见技术研究。独立 GitHub 仓库 `sair-math-dev/pebble` 已建立，设计在 `design/product-architecture` 分支维护；应用尚未实现。

## 9. 实施顺序与验收

第一阶段完成 Cargo 式发布与复用闭环：账户/组织、包清单、依赖解析与锁定、本地构建检查、包注册、Slate 检查适配、不可变发布，以及采用 GitHub 熟悉导航的研究卡、源码、版本、依赖和独立结果页面。搜索支持结果及包，结果页面提供明确假设、署名、引用与使用示例，并提供直接复用的反向列表。论文作为可提交附件阅读和引用；外部源码仓库链接可用，完整 Git 托管不阻塞发布。以两个不同主题的研究项目和一个仅含引理的包验证产品模型。

验收应演示：从搜索发现并安装固定版本 → 在外部项目中引用并导入结果 → 完整检查 → 正式发布 → 第三方重现。还必须证明源码或依赖被替换、缺少证据、检查失败、开发假设、无权读取私有材料时不能取得正式验证发布。

第二阶段完善结果与引用图、关注动态、通知、议题和外部项目接入；验证论文与代码更新时的引用版本及项目审阅体验。写作编辑和实时协作不列入当前实施阶段。

第三阶段建设竞赛、学习路径及受权限控制的研究记录导出；以默认贡献、退出、私有项目、协作者权限和受保护评估的完整场景验收。训练、基础设施和模型服务可由各自团队并行推进，这里的顺序仅描述 Pebble 的交付依赖。

产品效果关注从发现到成功复用的时间、第三方重现成功率、可复用成果及后续贡献、协作完成率和发布失败原因。模型评估、科学重要性与平台活跃度分别衡量。

## 10. 下一轮设计需要落定

1. 结果页、项目页与论文阅读的交互原型，特别是自然语言陈述与精确声明如何并排关联。
2. Slate 当前实际提供的包、导入、验证与证据接口，以及缺失的协议能力。
3. Git 托管与外部仓库同步策略、论文提交格式及外部研究环境的成果接入接口。
4. 包命名、版本兼容约定、引用标识与归属转移规则；DOI 等外部集成另行核实。
5. 训练选择、协作者授权和数据撤回的具体政策与用户流程。

以上问题不阻止产品对象和主流程设计，但必须在相应实现开始前形成具体决策。
