# Pebble 容量目标

范围修订：用户后续明确研究仓库完整基于 Git。下文实测针对已有快照 API；Git clone/fetch/push、pack CPU/内存、仓库对象与 refs 数量、历史保留及 Git 备份尚未压测，不能用当前 HTTP 基线推算这些能力。

状态：2026-09-09 的初始容量模型与本地混合读取实测。用户已确认首阶段目标是 **1 万注册用户**；最终参考 Hugging Face 的平台规模演进。已在 10,000 个真实账户的数据上完成 35/100 RPS 两档测试，范围见第 5 节；**尚未完成生产容量与 SLO 验收**。注册数、DAU、在线会话和同时处理的请求分别计量。

## 1. 初始工作负载假设

先以小型理论/定理包验证服务。以下参数用于选择首批实例和设计压测，均可按运营数据替换；不是对上传内容或科学领域的特殊接受条件。

| 参数 | 正常日假设 | 活跃日假设 |
| --- | ---: | ---: |
| 注册用户 | 10,000 | 10,000 |
| DAU / 注册用户 | 10%：1,000 | 30%：3,000 |
| 峰值在线会话 | 100 | 300 |
| 每日每活跃用户 API 请求 | 50 | 50 |
| API 请求总量 / 日 | 50,000 | 150,000 |
| 平均 API RPS | 0.58 | 1.74 |
| 峰值 / 平均倍数 | 20 | 20 |
| 估计峰值 API RPS | 12 | 35 |
| 每日每活跃用户下载 | 3 次，每次 2 MiB | 同左 |
| 下载量 / 日 | 5.86 GiB | 17.58 GiB |
| 发起检查的活跃用户比例 | 5%，每人 2 次 / 日 | 同左 |
| 检查任务 / 日 | 100 | 300 |

`平均 RPS = DAU × 请求数 / 86,400`；在线会话大部分时间在阅读、思考或本地计算，不持续占有一个 API 工作线程。上传、检查轮询、探索 DAG 和大文件下载须分别统计，不能只测轻量元数据 GET。

“1 万 DAU”按同样请求频率约为 5.8 平均 RPS、116 峰值 RPS；“1 万同时活跃会话”若每会话每 5 秒发一次请求则是 2,000 RPS。两者均超出当前已确认口径，不能从“1 万注册用户”偷换得到。

## 2. 首批资源与服务目标

下面是待实测的采购/配置起点，不是性能保证或已批准的采购。部署地区、供应商、预算仍待确定。

| 组件 | 起点 | 扩容依据 |
| --- | --- | --- |
| 无状态 API | 两个故障域各 1 实例；每个 2 vCPU、1–2 GiB | p95/p99 延迟、错误率、事件循环延迟、CPU、内存及连接池等待 |
| PostgreSQL | 托管主库 + 可用区故障切换；2–4 vCPU、8–16 GiB、SSD | 慢 SQL、锁等待、活跃连接、WAL/IO、索引及存储增长 |
| 验证 worker | 两个专用 Linux 实例；每实例 2 vCPU、4 GiB，初期每进程 1 个任务 | 最老可领取任务年龄、任务耗时分布、超时/OOM比例 |
| S3 | 私有托管 bucket，版本保留及备份政策 | 数据量、请求量、出口流量、恢复时间 |
| 入口 | 托管 TLS 负载均衡及限流/WAF | 连接数、带宽、拒绝率与请求体大小 |

单机生产 Compose 是可移植的启动资产，**不提供双故障域高可用**。两份容器副本若在同一宿主机仍共享故障点。worker 的专用 VM 也不能与 API、数据库混布后仍宣称它们故障隔离。

待验收 SLO：元数据 API 可用性 99.9% / 月；在约定负载下小响应 p95 < 300 ms、p99 < 1 s；正常队列等待 p95 < 60 s。上传传输时间、下载大响应及 Slate 检查时长单独报告。30 天月的 99.9% 错误预算约 43.2 分钟。上述 SLO 尚未测得，也不是已经承诺的 SLA。

连接池按总部署计算：例如 `2 API × 12 + 2 worker × 4 + 10 运维余量 = 42` 个连接。`DB_POOL_SIZE` 已实现，接受 1..100，默认 12；上述 worker 的 4 需显式配置。扩容副本前重算连接预算，预留迁移与恢复连接；需要事务级池化时先验证驱动、会话设置和事务语义，再接入 PgBouncer。PostgreSQL 连接上限同时影响服务器资源，不能只增加应用副本。[PostgreSQL 连接设置](https://www.postgresql.org/docs/current/runtime-config-connection.html)。

## 3. 检查队列与成本

假设平均一次完整准备和检查占槽 10 秒，峰值到达率 10 个 / 分钟，为把利用率控制在 70% 以下，所需槽位约为 `ceil(10/60 × 10 / 0.7) = 3`。若真实平均时长是 30 秒则需要 8 个槽位。两个初始单任务 worker 可处理低频日常流量；突发时应排队并提示等待，而不是同时启动所有检查或伪造通过状态。

这些耗时是假设。实际测量应包括固定依赖下载、内容校验、rootfs/源码准备、Slate 解析和检查、报告收集与提交；另列内核检查时间以便归因。失败、超时、资源耗尽和没有证据分别计数，超时不表示命题为假。

PostgreSQL 的 `FOR UPDATE SKIP LOCKED` 适用于多个消费者争领队列表；需要结合租约、attempt 绑定、重试和幂等提交。该机制本身不证明检查完整或发布原子性。[PostgreSQL SELECT](https://www.postgresql.org/docs/current/sql-select.html)。

初期通过 worker 实例数控制并发。每个实例有独立 scratch 目录和 cgroup 内存/CPU/进程限制；耗尽时任务保持未完成，由租约恢复路径处理。不要让用户请求直接选择工具链、宿主路径或任意资源上限。增加并发前先按最坏允许包体估算下载缓冲、Base64/JSON副本、报告、Slate 内存与临时磁盘。

## 4. 配额与背压

当前协议上限来自 [protocol.ts](../src/protocol.ts)，HTTP 体上限来自 [server.ts](../src/server.ts)，验证限制属于固定政策。部署不得把一个较宽的入口限制当成服务已支持更大的包。JSON/Base64 上传的 HTTP 字节数也不等于源码字节数。

已实现的限额如下；调整它们需要重新评估最坏输入与拒绝行为。

| 控制 | 当前实现 | 饱和时的行为 |
| --- | --- | --- |
| IP 请求频率 | 每 API 进程按可信客户端 IP 计数；GET 180 次/分钟，写请求 30 次/分钟；health 豁免 | 429；跨副本总额度尚需共享设施 |
| 每账户待处理检查 | 4 个排队或运行任务；首次创建与 retry 共用额度 | 429，已接受任务保留可查询身份 |
| 全局待处理检查 | 数据库事务控制总共 1,024 个；首次创建与 retry 共用 | 429，已有任务继续处理 |
| API 请求并发 | 每进程总共 64，其中大响应/上传请求最多 2；包括快照上传/下载及候选详情 | 503 + Retry-After，health 豁免；客户端断开后仍等待后台处理结束才归还工作额度 |
| 包体与依赖预算 | 源内容最多 32 MiB/4,096 文件；HTTP body 48 MiB；锁定依赖图最多 1,024 包、256 MiB/16,384 文件 | 拒绝超限输入，不把部分内容标为完整通过 |

尚未实现的运营额度包括每账户 API 总速率、每小时检查次数和账户/组织累计存储/出口记账。初始候选值可设每账户 120 API 次/分钟、10 次检查/小时，并按试用反馈调整；它们不能当作当前保护。队列最老等待超过 15 分钟时应告警、扩容或暂停新增，但当前没有自动按该阈值拒绝的功能。存储超额的处理要保留已发布精确引用，不得自动删除其对象。

用户已决定先邀请制：运维签发单次、限时、可撤销邀请，不开放自主注册或无限转邀；签发、兑换及客户端已实现，兑换接口有单独 1 KiB 体上限和每 API 进程单 IP 5 次/分钟限制。初期扩额人工批准，新增累计资源记账尚待实现。学术声誉用于展示可追溯贡献，不直接豁免资源限制；多账户和多副本仍需要平台硬预算。以下 Git、独立归档与累计成本保护均是待实现要求，不能由上述快照限额推断已经具备：

| 风险 | 准入与背压要求 |
| --- | --- |
| 海量小包、版本及长期归档 | 按稳定账户/组织及平台总额限制累计字节、对象、版本和元数据数量；归档先在有限免费额度、机构预算或获批容量内接纳，不承诺无条件无限免费保留 |
| 准备失败或删仓重建绕过额度 | 准备前原子预留，绑定幂等操作；发布后转为长期占用，删仓/改名/重建不返还。失败预留须停止在途写入并清理临时资源后释放，另限暂存与孤儿对象 |
| 小文件树携带巨大 Git 历史，pack/clone 消耗 CPU | 对 push、clone/fetch 与归档分别限制展开字节、对象/refs、历史成本、CPU/内存/时间及账户/全局并发；单包 32 MiB 不代表历史上限 |
| 反复检查与 retry 占满 worker | 在现有 pending 上限之外限制每时段次数和计算预算，重试计入成本，按账户公平调度；邀请制不替代全局并发和预算 |
| 撤销传播、反向图与依赖 ACL 查询放大 | 设置查询时间、扫描、节点/边和输出预算，有界处理反向传播；当前权限与有效性仍逐请求复查，不能等待异步传播才拒绝读取 |

多副本不能依靠每进程内存计数器兑现“全局限流”。账户级限额使用共享、事务一致的状态或独立网关；入口的 IP 归属也要可信。未设置 `TRUST_PROXY_CIDRS` 时 API 不信任转发头；生产 Compose 已固定 Caddy 地址并仅信任该 `/32`。托管入口使用实际受控代理网段，同时禁止外部绕过入口直接连接 API。不能为得到客户端 IP 而信任任意 `X-Forwarded-For`。

定理图探索后续还需独立节点、边、字节、调用和时间预算。预算耗尽仅表示此次探索停止。当前发布/包服务的压测不能冒充全局 DAG 的探索能力或容量。

## 5. 可复现的验收

已运行 [capacity-probe.ts](../tests/capacity-probe.ts)，最终原始记录为 `.artifacts/capacity-probe-2026-09-09T09-09-47.331Z.json`，包含实际源码文件 SHA256、工具链/政策身份、运行参数与清理记录。数据由 10,000 条真实 principal 及 token 索引组成；真实 Slate worker 检查并 HTTP 发布一个包含 Apache 2.0 许可证、3 文件、13,858 bytes 的代数包后才开始读取测试。4,050 次请求使用不同的已持久化有效账户，每个响应还核对 payload。

环境为 Node v24.20.0、Linux x64、Ryzen 9 7950X3D（32 logical CPUs），同机真实 PostgreSQL 与 MinIO；负载生成器独立进程、按固定时间开放式发请求。流量为 registry meta 10%、包信息 40%、精确版本 40%、小快照下载 10%。测试入口仅信任 loopback，模拟 100 个客户端 IP。后续邀请测试发现当时限流插件的路由钩子未正确安装；本轮已修复并验证真实拒绝行为，以下历史吞吐数据未在修复后重测，不能作为限流有效性的证据或当前性能基线。该隔离实例关闭请求日志，生产日志成本没有包含在内。

| 指标 | 35 RPS，30 秒 | 100 RPS，30 秒 |
| --- | ---: | ---: |
| HTTP 200 / 正确 payload | 1,050 / 1,050 | 3,000 / 3,000 |
| p50 / p95 / p99 延迟 | 3.06 / 7.50 / 8.64 ms | 2.21 / 5.77 / 6.76 ms |
| 响应 bytes | 2,650,095 | 7,571,700 |
| 同时在途请求峰值 | 1 | 1 |
| API CPU（单核百分比） | 5.20% | 7.51% |
| API RSS 采样峰值 | 271.9 MiB | 318.5 MiB |
| DB 连接峰值 / 等待者峰值 | 1 / 0 | 1 / 0 |

后段已经预热，较高 RPS 的较低延迟不说明增加负载会改善性能。CPU 只包含 API 及其 DB/S3 客户端，不包含独立数据库/MinIO 服务；生成器 CPU/RSS 在 JSON 中另列。RSS 为周期采样，不能作为连续最大值。这个测试没有逼近饱和点，也没有覆盖 WAN/TLS、长尾大包、私有授权分布、多副本、并发上传、持续写入或普通定理检查吞吐，不能当作架构最大吞吐、1 万并发或云 SLO。单个小包的 worker 检查耗时约 48.74 ms，仅有一个样本。

生产验收继续使用固定 API 镜像、Slate rootfs、政策、数据库版本和代表性数据集，保留并发、请求类型、原始统计与运行地区。除上述本地读取外，以下仍是目标环境的验收项目，不应因列出步骤就视为已完成：

1. 跑真实发布、下载与干净 Slate 客户端复用；验证撤权、依赖替换、重复任务和竞争发布在压测时仍正确。
2. 用 12、35、70、140 RPS 梯度测混合元数据流量；分别测上传、下载、任务提交和轮询，记录数据库锁及连接等待。
3. 注入 10 个任务 / 分钟的短时突发，测排队、吞吐、超时和恢复；停止一个 worker，确认租约收回后没有重复正式发布。
4. 停止一个 API，演练 PostgreSQL 故障切换及一次完整备份恢复；恢复后重新读取引用并校验实际 blob 摘要。

[load.mjs](../deployment/load.mjs) 是有调用/时间/并发上限的 GET 探针，可用于真实包元数据或授权下载端点：

```sh
node deployment/load.mjs --url http://127.0.0.1:3000/api/v1/meta --rps 2 --seconds 60 --concurrency 8
```

`/meta` 仅是轻量探针，示例按单 IP 限额控制到 2 RPS；测试真实读取时替换为实际包 ID 的元数据或下载路径。私有读取从环境变量 `PEBBLE_LOAD_TOKEN` 取 token，报告不会输出它。探针输出目标/实际 RPS、负载机主动丢弃的请求槽、错误码、传输字节和延迟分位数。负载机跟不上也会失败，不能算作 API 的成功压测；它不生成账户、不替代混合流量或验证任务测试。运行公网压测前明确目标和预算，先在隔离预生产环境执行。

## 6. 向更大规模演进

注册数是下面的规划阶段标记，实际触发条件来自吞吐、数据量、延迟和故障演练。并非注册数一到就自动拆服务，也不是对 Hugging Face 当前用户规模的统计。

| 阶段 | 触发瓶颈 | 迁移能力 | 验证门槛与必须保留的语义 |
| --- | --- | --- | --- |
| 1 万注册 | 首批流量、单机故障点、检查排队、运营配额缺口 | 两个故障域的无状态 API、独立 worker 池、托管 PG/S3；补齐共享限流与账户记账 | 真实内容混合负载、授权撤销/重试/发布竞争、故障切换与恢复；继续固定快照、工具链及检查输入 |
| 10 万注册 | 出口/上传内存、连接预算、队列年龄或读写争用达到阈值 | 先完成流式与可恢复 blob 传输，再扩大包上限；API/worker 分别扩容，连接池化和授权分发层 | 最坏包体下有限内存、断点重传与摘要核对、并发上传限额；分发每请求检查当前授权，已签发链接的 TTL 不能替代撤权 |
| 百万注册 / 大量成果 | 索引规模、搜索/图读取影响事务写入，元数据及对象增长影响备份窗口 | 搜索/邻接投影、读副本/分区、分级对象存储；只有实测需要时迁移队列并使用 outbox | 投影延迟不泄漏已撤权内容，精确版本和证据可回源核验；压测长尾数据与恢复窗口，保留幂等任务和原子发布 |
| 跨区域、HF 级演进目标 | 区域延迟、数据驻留、出口费用、单区域灾难及运维规模 | 明确写入归属、跨区域对象副本与恢复、授权控制面、分区容量治理 | 区域失效及撤权传播实测；权限状态不可判断时拒绝读取，不把历史副本当当前授权；引用与署名保持稳定 |

当前 JSON/Base64 整包传输会产生多份内存副本。流式上传/下载、分段或可恢复传输必须先设计好服务端摘要、不可变提交、授权与中断清理，再放宽包体限制。CDN 可缓存不可变 bytes，但私有内容及可撤销的公开状态需要每请求通过当前授权判定；只有短 TTL 或定期清缓存仍不满足即时撤权。

当 PostgreSQL 的搜索/邻接读影响事务写入时，再考虑独立搜索投影、只读副本和分区。发布与权限判断继续以事务数据为准。只有任务量、路由或延迟证实 PostgreSQL 队列不合适时才更换队列系统，并保留 outbox 与幂等语义。

再向多区域部署推进时，需要明确写入归属、数据驻留、私有权限撤销传播及区域灾难恢复。大规模研究成果与长期引用会使对象存储、出口流量、索引、滥用处理和运维成为不同容量问题。Hugging Face 级平台是演进目标；当前无相应用户、数据、吞吐或恢复实测，不能用初版架构图宣称已经达到。
